# Day 07 — .gitignoreを理解（2026-08-20）

## やったこと
- `.gitignore` を作成（`.env` と `*.log` を登録）
- `git status` から対象ファイルが消えることを確認
- `.gitignore` 自体をコミット
- **`git add .` を解禁**し、Day03 との結果の違いを比較
- `.gitignore` の罠を実演（追跡中のファイルに追加してみる）

## わかったこと
- `.gitignore` は「Gitに無視してほしいファイル」のリスト。`*` は「なんでもいい」を意味するので `*.log` で `.log` 終わりを一括指定できる
- **`.gitignore` 自体はコミットして共有する。** チーム全員が同じものを無視する必要があるため
- 3つは別物

| 状態 | 意味 |
|---|---|
| 無視されている | `.gitignore` に書いてある |
| まだaddしていないだけ | 書いていない未追跡ファイル |
| ファイルが消えた | `.gitignore` では消えない。ディスク上には残っている |

- `git add .` の結果が Day03 と変わった

```
Day03:  A  .env / A  docs/design.md / A  tmp.log   ← 事故
Day07:  A  docs/design.md                          ← .gitignore が防いだ
```

## 一番の罠
- **`.gitignore` は、一度コミットしたファイルには効かない。**
  - Gitはファイルを「未追跡」と「追跡中」に分けていて、`.gitignore` を見るのは**未追跡のファイルだけ**
  - 実演：コミット済みのファイルを `.gitignore` に追加してから編集 → `git status` に普通に出てくる
- 外したい場合は `git rm --cached ファイル名`（`--cached` を付けないとファイルごと消える）
- ただし**過去のコミットからは消えない。** 秘密情報を push してしまった場合の正しい対処は、履歴を消すことではなく **その秘密情報自体を無効化・再発行すること**
- したがって **`.gitignore` はプロジェクトの最初に書くのが鉄則**
